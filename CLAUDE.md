генерация постов/каруселей/сценариев, инста-воронка с PDF, монтаж видео, публикация после

зовёт агента-исполнителя напрямую через `claude -p`, а результат постит от имени его бота.

## Как разговаривать с клиентом (это важнее любого технического правила)

**Клиент только начинает разбираться в IT.** Слова, которые нам кажутся бытовыми — «задеплоить»,
«переменная окружения», «репозиторий», «SSH», «systemd», «токен», «порт», «домен», «рестартнуть
сервис» — для него пустой звук или повод испугаться. Он предприниматель, а не разработчик, и
пришёл за результатом: чтобы посты выходили, а не чтобы изучать Linux.

Поэтому Claude, который работает на его стороне, обязан общаться **максимально просто**. Это не
пожелание к тону, это требование к продукту: если клиент не понял инструкцию — продукт не работает,
даже когда код идеален.

### Правила общения

1. **Никакого жаргона без перевода.** Термин можно произнести один раз, но сразу рядом — простыми
   словами, что это. Не «сделай деплой», а «выложи новую версию программы на сервер — это как
   обновить приложение на телефоне».
2. **Один шаг за раз.** Не выдавать список из десяти пунктов. Дать одно действие → дождаться, что
   получилось → следующее. Клиент не должен держать в голове план целиком.
3. **Говорить, куда нажимать и что печатать, дословно.** Не «открой конфиг и поправь переменную»,
   а «открой файл вот по этому пути, найди строку, которая начинается со слова TG_CHANNEL_ID, и
   замени всё после знака = на …». Команды давать готовыми к копированию, целиком, одной строкой.
4. **Предупреждать, что сейчас произойдёт и как понять, что получилось.** Перед каждой командой —
   одна фраза «сейчас мы…», после — «если всё хорошо, ты увидишь …; если увидишь другое — покажи
   мне, что написано». Клиент не умеет отличать нормальный вывод от ошибки, и это нормально.
5. **Не предполагать, что он умеет пользоваться терминалом, git, SSH или редактором кода.** Если
   шаг требует терминала — объяснить, как его открыть, прежде чем давать команду.
6. **Ошибки переводить на человеческий.** Не показывать стек вызовов и не цитировать лог целиком.
   Сказать: что сломалось, чем это грозит (или не грозит), что сделать. Пример: не
   «ECONNREFUSED 127.0.0.1:443», а «сервер сейчас не отвечает. На публикацию это не влияет —
   ничего не потерялось. Давай проверим, запущена ли программа».
7. **Никогда не винить клиента.** «Ты неправильно сделал» → «давай перепроверим этот шаг, там
   легко промахнуться». Если он что-то сломал — сначала чинить, потом (коротко) объяснять.
8. **Не грузить внутренностями продукта.** Фазы, тикеты, миграции БД, названия модулей — это наша
   кухня. Клиенту нужно знать только: что система делает, куда писать, на что нажимать и что
   делать, если не работает.
9. **Спрашивать простыми вопросами.** Не «какой у тебя IG_MODE?», а «публикация в Instagram у тебя
   сейчас настроена через приложение Meta или через вход в аккаунт браузером? Если не знаешь — я
   сам посмотрю».
10. **Уточнять, понятно ли — но не навязчиво.** Раз в несколько шагов: «тут всё понятно, идём
    дальше?». Клиент стесняется признаться, что потерялся, поэтому спрашивать должен Claude.

### Словарик — как называть вещи в разговоре с клиентом

| Наше слово | Как говорить клиенту |
|---|---|
| деплой, выкатка | выложить новую версию на сервер (как обновление приложения) |
| VPS, сервер | компьютер, который работает круглосуточно и на котором живёт система |
| SSH | защищённый вход на этот компьютер с вашего ноутбука |
| репозиторий, git | папка с проектом и историей всех изменений |
| переменная окружения, `.env` | файл с настройками и паролями системы |
| токен, ключ доступа | длинный пароль, по которому программа заходит в сервис вместо вас |
| systemd, сервис | то, что само включает программу и не даёт ей выключиться |
| Nginx, статика | раздача картинок и PDF в интернет по ссылке |
| логи, journalctl | дневник, куда система записывает, что делала |
| рестарт | выключить и включить обратно |
| миграция БД | обновление структуры хранилища — делается само, вмешательства не требует |
| смоук, тесты | самопроверка: система проверяет сама себя и говорит «всё цело» |

### Чего клиент делать НЕ должен (и это не его вина)

Он не настраивает сервер, не правит код, не разбирается в логах. Всё это наша часть работы или
работа его Claude. Клиент делает ровно три вещи: **пишет задачи в Telegram**, **нажимает
«Одобрить»** и **наполняет мозг бренда**. Если инструкция требует от него чего-то ещё — значит,
инструкция плохая, а не клиент плохой.

## Архитектура (двухмозговая — запомни это первым)

Система живёт на **двух машинах**, и это влияет на каждое решение:

- **VPS (always-on, всё на аккаунтах клиента):** Node-диспетчер + 6 Telegram-ботов + SQLite +
  Nginx-статика. Здесь идут тренды, генерация текста/картинок/PDF, согласование, публикация.
- **Ноут клиента (по требованию):** видео-монтаж реального материала через **локальный Claude
  Code**. Готовый Reels авто-заливается в очередь согласования на VPS. Видео — НЕ часть
  VPS-деплоя, ставится отдельно на машину клиента.

**Набор скиллов, который уезжает клиенту вместе с видео-пайплайном** (решение владельца,
07.09.2026): `hyperframes` (обязательная точка входа в любую видео-задачу), `hyperframes-cli`,
`motion-graphics`, `embedded-captions`, `general-video` и **`remotion-to-hyperframes`** — на
случай, если у клиента или его подрядчика уже есть готовые Remotion-композиции: скилл переносит
их исходники в HyperFrames, вместо того чтобы собирать заново. Ставить скиллы вместе, поодиночке
они бесполезны: `hyperframes` маршрутизирует задачу в остальные.

## Правила, нарушать которые нельзя (billing / bans / ToS)

1. **Весь интеллект — только через вызов Claude Code как подпроцесса** (`claude -p "..."`), на
   Pro-подписке клиента. **Node НИКОГДА не ходит в Anthropic API напрямую** — прямой API это
   отдельный платный ключ, подпиской не покрыт. Диспетчер = «тупая труба» (маршрутизация,
   очередь, кнопки, расписание), он не думает.
2. **App Review в Meta не проходим.** Публикация — только в собственные аккаунты клиента, двумя
   путями на выбор (`IG_MODE`), и **оба остаются в коде**:
   - `api` — Graph API в **dev-mode** (клиент = админ/тестер приложения), прав, требующих ревью,
     не запрашиваем;
   - `browser` — **вход в аккаунт клиента живым браузером** и публикация через веб-интерфейс
     (решение владельца 15.09.2026: настройка Meta-приложения оказалась слишком трудоёмкой для
     клиента). Это **нарушает правила пользования Instagram**, и риск несёт аккаунт клиента, а не
     сервер. Решение принято осознанно и записано здесь, чтобы через полгода никто не счёл его
     случайностью. Что при этом делается и чего сознательно НЕ делается —
     в `specs/ig-browser-publish.md`; средств обхода антибот-проверок в коде нет.
3. **Инста-DM с PDF идёт через ManyChat**, не через сырой API. В самом инста-DM файл-PDF
   технически невозможен → отдаём **ссылкой** на Nginx-статику или уводом в Telegram.
4. **Тренды — через Apify** (решение клиента 07.09.2026, заменило вариант C). Актор Apify ходит в
   соцсети со своей стороны: мы **никуда не логинимся**, cookie-сессий и прокси нет, бан-риска для
   аккаунта клиента нет. Лимит «1 прогон/день» остался, но теперь он про **деньги** — каждый прогон
   актора платный. Вариант C (логин основным аккаунтом) — резерв и **не реализован**; включать его
   без резидентного прокси, постоянной cookie-сессии и человекоподобного темпа нельзя.
   **Не путать с правилом 2:** с 15.09.2026 на VPS появилась браузерная сессия аккаунта клиента,
   но она только **публикует**. Использовать её для сбора трендов нельзя: публикация — это
   несколько действий в неделю, а парсинг лент — сотни запросов, и именно он приводит к блокировке.
5. **Telegram Bot API качает файлы только до 20 МБ** — поэтому сырое видео НЕ заносится через
   бота; монтаж локальный. Готовый лёгкий ролик заливает на VPS сам локальный CC.
6. **3 отдельных согласования по площадкам** — форматы разные (TG посты+фото / IG карусели-Reels
   / Threads только текст). Не объединять в одно «опубликовать везде».
7. **Все сервисы — на аккаунтах клиента** (Pro-подписка, VPS, ManyChat Pro, Apify, прокси,
   Meta-app, Figma). Мы настраиваем и передаём, не платёжный посредник.

## Агенты (7)

|---|---|---|

Итого до 9 ботов и 9 топиков.

## Соглашения по файлам (для хендовера — соблюдать всегда)

Проект целиком передаётся клиенту папкой; на его ПК Claude Code должен прочитать всё и понять
без нас. Поэтому:

- **Каждый агент — свой отдельный markdown-файл** в `agents/` (напр. `agents/producer.md`,
  `agents/scout.md`, … по одному на каждого из 7). Оформление — как у CLAUDE.md: самодостаточный,
  человекочитаемый. НЕ прятать определение агента внутри графа/тикетов/кода — так его легко
  найти и передать.
- **Создание/оформление агента — всегда через скилл `/agent-development`**, и запускать его
  ТОЛЬКО в самом конце сессии, когда пользователь полностью утвердил агента. Порядок: сперва
  согласовать поведение агента с пользователем маленькими шагами → получить «ок» → и лишь затем
  финализировать файл агента скиллом. Не запускать скилл на черновике. Напоминания от
  пользователя не ждать — это правило по умолчанию.
- **Ничего не прячем.** Значимые файлы (доки, спеки, карта, конфиги) — на видных местах в дереве
  репозитория, осмысленные имена. Не складывать нужное в скрытые dot-папки и не размазывать по
  временным каталогам. Исключение — только реальные секреты: они в `.env` (в git не коммитить).
- Каждый модуль оставляет свою спеку в `specs/`; общая карта проекта — в видимом месте репозитория.

## Окружение (секреты — только в .env, в git не коммитить)

Понадобятся: токены 6 TG-ботов, ID общей группы, путь к SQLite, `TG_CHANNEL_ID`.
**Доступ:** `OWNER_IDS` — user_id тех, кому боты вообще отвечают (через запятую). Пусто = отвечают
всем подряд, кто нашёл бота; на боевом сервере заполнять обязательно.
**Тренды:** `APIFY_TOKEN` + id акторов (`APIFY_ACTOR_IG`, `APIFY_ACTOR_THREADS`), а кого смотреть —
в `trends/sources.json` (не секрет, видимый файл). **Публикация IG/Threads:** `IG_USER_ID` +
`IG_ACCESS_TOKEN`, отдельно `THREADS_USER_ID` + `THREADS_ACCESS_TOKEN` (**разные приложения и
разные токены**), плюс `PUBLIC_DIR` и `PUBLIC_BASE_URL` — без публичной статики IG не опубликует
карусель. **Публикация браузером (T19, вариант C):** `IG_MODE=browser` + `IG_LOGIN` и
`IG_PASSWORD` — и всё; токены Meta, `THREADS_*` и публичная статика для постов не нужны.
Необязательные `IG_PROFILE_DIR`, `IG_SHOTS_DIR`, `IG_HEADFUL`. **Папку профиля нельзя терять и
нельзя коммитить** — в ней живые куки входа, то есть фактически те же креды (она в `.gitignore` и
бэкапится вместе с `brand-brain/`). **PDF-воронка (T13):** те же `PUBLIC_DIR`/`PUBLIC_BASE_URL` (по ним раздаются PDF), а сами
три темы — в видимом `manychat/funnel.json` (не секрет). **Воронка (T14):** `MANYCHAT_TOKEN`
(ManyChat → Settings → API, тариф Pro), опционально `MANYCHAT_FIELD_PREFIX` и `MANYCHAT_DRY_RUN=1`.
**Видео (T15):** те же `PUBLIC_DIR`/`PUBLIC_BASE_URL` (Reels публикуется по `video_url`), плюс
необязательные `VIDEO_PUBLIC_SUBDIR` и `VIDEO_MAX_MB`; доступ ноутбука к серверу — в `video/vps.env`
на самом ноутбуке, не в репозитории. **Фаза 5 (T16):** необязательные `BOT_TOKEN_VIDEO`/`TOPIC_VIDEO`
и `BOT_TOKEN_ANALYST`/`TOPIC_ANALYST`, а также `ANALYTICS_AT`, `ANALYTICS_WEEKDAY`, `ANALYTICS_DAYS`
и `ANALYTICS_INSIGHTS=1` (метрики площадок — только если у токенов клиента есть права
`*_manage_insights`). **«Мозг бренда» (T18):** необязательные `BOT_TOKEN_BRAIN`/`TOPIC_BRAIN` —
больше ничего не нужно, пути к «Входящим» и `materials/` выводятся из `brand-brain/`.
На локальной отладке — тестовые боты; резидентный прокси нужен только резервному варианту C,
который не реализован.

## Гочи

- **Личка бота открыта миру, пока не задан `OWNER_IDS`.** Роутер спрашивает «в правильном ли месте
  написали», а не «кто написал»: любой, кто узнал @username бота, пишет ему в личку, и каждое такое
  сообщение уходит в `claude -p` на Pro-подписку клиента. `OWNER_IDS` (09.09.2026) закрывает и текст,
  и кнопки карточек; пустое значение оставлено рабочим нарочно — иначе первый запуск, когда user_id
  ещё неизвестны, выглядел бы как «все боты сломались». Свой id клиент узнаёт из строки `[access]`
  в логе после попытки написать боту.
- Локальная отладка ≠ хендовер: сбор трендов (нужен токен Apify), публикацию IG/Threads (Meta-
  приложения + Nginx-статика) и ManyChat **до конца проверить без аккаунтов клиента нельзя** —
  только на деплое. Репетиция публикации без последствий — `PUBLISH_DRY_RUN=1`.
- «Мозг бренда» поставляется **пустым**; агенты обязаны читать его перед задачей — при пустом
  слоте контент будет обезличенным (это ожидаемо до наполнения клиентом).
- Матчинг темы в инста-воронке — **3 кнопки/ключа**, без ИИ-классификации (дешевле, не мажет).
- **Рендер визуала не «рисует картинки».** Слайд собирается вёрсткой: типографика + геометрическая
  подложка-мотив по ключевым словам из поля `Визуал`. Иллюстраций по описанию никто не генерирует —
  это отдельная история, в T10 её нет. Не обещать клиенту иное.
- **На VPS без шрифтов с кириллицей слайды выйдут квадратиками** — ставить `fonts-dejavu`/
  `fonts-noto-core` вместе с браузером. Шрифт не встраивается, берётся системный.
- **PDF: «A4» словом ≠ 210 мм.** Chromium считает бумагу A4 как 594.96×841.92 pt (209.89×297.0 мм),
  и лист ровно в 210 мм в неё не влезает — каждая страница роняет полоску на следующую, 5 страниц
  превращаются в 11. Размер листа задан числом (794×1123 px) и одинаков в `@page`, в `.page` и в
  вызове `page.pdf()`; разрыв страницы стоит ПЕРЕД листом (`break-before`), иначе к каждому листу
  добавляется пустой. Без `printBackground: true` документ печатается вообще без фонов.
- **Плейсхолдер в комментарии шаблона тоже подставляется.** `{{PAGES}}` в документирующем
  комментарии `render/templates/pdf.html` вставил туда копию всех страниц, и документ собрался
  дважды. В шаблонах писать имена ключей без фигурных скобок.
- **`file_id` в Telegram привязан к боту.** Картинку, загруженную ботом Дизайнера, бот Издателя
  по её `file_id` отправить НЕ может (`Wrong file identifier/HTTP URL specified`). Если кадры шлёт
  другой бот — грузить файлы заново. Ровно это поймал живой прогон T10.
- **Telegram принимает media-group строго от 2 до 10 элементов** — одиночная обложка уходит
  `sendPhoto`, карусель длиннее 10 кадров режется на группы. Совпадает с лимитом карусели Instagram.
- **Весь ответ агента = один элемент очереди.** Никто не режет ответ на части, поэтому «Одобрить»
  публикует `content` целиком. Для 2–3 вариантов Сценариста это решается кнопками «Вариант N»
  (выбор переписывает `content`), а для Threads — тем, что агент отдаёт один пост. Любой новый
  формат «несколько штук в одном ответе» надо будет решать так же явно.
- **API ManyChat не умеет создавать флоу.** Он читает и пишет поля/подписчиков — и всё. Поэтому
  воронка собирается пополам: диспетчер держит в bot-полях (`pdf_<ключ>`) актуальные ссылки, а
  сообщение с тремя кнопками и триггеры человек заводит в UI один раз по карточке
  «/воронка настройка». Обещать клиенту «настроим воронку полностью автоматически» нельзя.
- **Ключ темы после запуска воронки менять нельзя.** Один и тот же `key` — это имя PDF-файла,
  часть публичной ссылки И имя bot-поля. Смена ключа (или `MANYCHAT_FIELD_PREFIX`,
  или `PDF_PUBLIC_SUBDIR`) ломает и разосланные ссылки, и флоу, который ссылается на старое поле.
- **Смена `PUBLIC_BASE_URL` тихо ломает директ.** В базе будет новая ссылка, а в поле ManyChat —
  старая, и человек получит 404. Поэтому диспетчер помнит, что именно записал (миграция
  `008_funnel_manychat`), и показывает расхождение в «/воронка». Лечение — «/воронка синх».
- **PDF-лид-магнит идёт МИМО очереди согласования.** Через очередь проходит то, что публикуется в
  ленту; лид-магнит лежит в статике и выдаётся по запросу в директе, поэтому `pdf_spec` в очередь
  не пускается, а владелец смотрит готовый файл в топике Презентатора (`/пдф <ключ>` — пересобрать).
- **Instagram НЕ принимает файл — только ссылку.** Graph API берёт `image_url`/`video_url` и качает
  медиа своими серверами, поэтому кадры из T10 перед публикацией копируются в веб-корень
  (`PUBLIC_DIR`) и уходят публичным https-адресом (`PUBLIC_BASE_URL`). Без этих двух переменных
  IG-карусель не опубликуется даже с идеальным токеном — это устройство API, а не недоделка.
- **У Threads свой API и свой токен** (`graph.threads.net`, отдельное приложение, права
  `threads_*`). Токен от Instagram там не работает — самая частая ошибка настройки.
- **Id поста в IG/Threads — 17–18 цифр** и в JS-число не влезает (2^53): тихо теряет последние
  цифры. Поэтому он хранится строкой в `published_ref` (миграция 006), а не в
  `published_message_id` (тот остался телеграмным).
- **Подпись к IG-посту берётся из `meta.caption`**, а не из `item.content`: у карусели content —
  это спецификация слайдов Дизайнера. Нет `caption` → пост уйдёт без подписи (об этом говорится
  в топике, но лучше, чтобы агент её отдавал).
- **Имена полей актора Apify не зашиты в код.** Вход (`directUrls` / `urls` / `startUrls`) и выход
  (`caption` / `postText`, `likesCount` / `stats.likes`) описаны в `trends/sources.json`. Смена
  актора = правка JSON. Побочный эффект `clean=true`: у части акторов пропадает `inputUrl`, тогда
  источник поста определяется по автору или остаётся пустым.
- **Ролик правится только перемонтажом.** На VPS нет ни исходников, ни монтажной, поэтому кнопка
  «Правка» на карточке ролика НЕ зовёт агента (это сожгло бы вызов `claude -p` впустую), а честно
  отвечает «перемонтируй на ноуте и залей заново». Текстовые черновики правятся как раньше.
- **Имя ролика с ноута нельзя брать как есть.** «Готовый ролик №3.MP4» в URL Meta не заберёт:
  при приёме имя приводится к `ГГГГММДД-ЧЧММСС-латиница.mp4`. Метка времени ещё и не даёт новому
  ролику затереть уже опубликованный по тому же адресу.
- **Заявка на монтаж создаётся ровно одна.** «Одобрить» можно нажать дважды (или переживить
  перезапуск планировщика) — от дубля монтажа спасает уникальный индекс `video_jobs(queue_id)`,
  а не аккуратность нажимающего.
- **Аналитику нельзя давать считать.** Цифры собирает код (`src/analytics/report.js`), агент их
  только объясняет — в промпте это сказано прямым текстом. Иначе он «посчитает» правдоподобно и
  неправильно, а проверить будет нечем.
- **Отметка автоотчёта живёт в БД, а не в памяти.** Иначе перезапуск диспетчера в понедельник
  вечером прислал бы второй отчёт за тот же день (`app_state`, миграция 011). Ставится ДО прогона.
- **Агенты не видят файлы, присланные в «Мозг бренда».** Агент — один проход `claude -p` с
  текстом: фото, видео, PDF он не открывает, а знает о файле только подпись из `09-inbox.md`.
  Поэтому бот просит подписывать файлы. Не обещать клиенту «агент посмотрит ваши фото».
- **Обновляя код на сервере, не перезаписывать `brand-brain/`.** В репозитории там пустые
  шаблоны, а на VPS — слоты, «Входящие» и файлы клиента. `rsync` без `--exclude 'brand-brain/'`
  молча сотрёт их шаблонами (`deploy/vps-setup.md`). По той же причине `brand-brain/` бэкапится
  отдельно: в базе и в git этих данных нет. **То же касается профиля браузера** (T19,
  `dispatcher/data/browser-profile/`): снесёшь — и вход придётся делать заново, с новым кодом
  подтверждения.
- **Профиль браузера — это креды, а не кэш.** Внутри живая кука `sessionid`: кто унесёт папку,
  зайдёт в аккаунт клиента без пароля. В git не коммитить, в архивы для передачи не класть,
  права на папку — только пользователю сервиса.
- **Вход в аккаунт делается ОДИН раз.** `npm run ig:login` не для «на всякий случай»: серия
  входов — самый заметный признак автоматизации, и именно она уводит аккаунт в проверку. Живая
  сессия проверяется командой «/вход статус», которая ничего не логинит.
- **«Входящие» читаются целиком перед каждой задачей.** Слот растёт сам, и каждая запись дорожает
  на каждом вызове `claude -p`. После ~15 тыс. знаков бот просит разнести главное по слотам 00–08.
- **Telegram не отдаёт просмотры постов канала.** Bot API их не показывает, поэтому в метриках
  Аналитика есть IG и Threads, но нет TG. Заводить ради этого пользовательскую сессию не будем.
- **Windows, `exit code 3221225794` (0xC0000142)** — подпроцесс `claude` не стартовал из-за нехватки
  ресурсов (на машине уже висит десяток `claude.exe`/`node.exe`/`cmd.exe`), а не из-за агента.
  `runClaude` повторяет запуск до 3 раз; если сыпется постоянно — закрыть лишние процессы. На VPS
  (Linux) гочи нет: там нет ни шима `.cmd`, ни промежуточного `cmd.exe`.
  Обратная сторона: механику повтора нельзя тестировать самим этим кодом — POSIX отдаёт код выхода
  одним байтом (3221225794 → 66), и на Linux повтор бы не включился. Поэтому `runClaude` принимает
  таблицу `transientCodes`, а смоук подделывает свой код (поймано на первом прогоне на VPS 09.09.2026).

## Рабочий процесс

- **Маленькими шагами** (см. глобальный `~/.claude/CLAUDE.md`): один под-шаг → пауза → показать
  результат → дождаться «ок». Не гнать несколько фаз подряд без паузы.
- Фазы-вехи сборки (внутренние): 0 фундамент → 1 ядро текста + согласование + TG-публикация →
  2 тренды + визуал + IG/Threads → 3 инста-воронка (3 PDF + ManyChat) → 4 видео на ноуте →
  5 полировка (Аналитик, автомонтаж, TG-нотификатор видео).
- Детали каждого модуля — в `specs/`.
