# Публикация в Threads и Instagram (T11 / T12)

Одобренный элемент очереди уходит в аккаунты клиента через **Meta Graph API в dev-mode**.
Threads и Instagram — **две разные площадки с двумя разными API**, и согласование у них тоже
раздельное (CLAUDE.md, правило 6): текст в Threads и карусель в IG никогда не публикуются «одним
нажатием на обе».

> **App Review мы не проходим.** Приложения создаёт клиент, он же админ/тестер, публикация только
> в его собственные аккаунты. Никаких прав, требующих ревью, код не запрашивает.

## Что где живёт

| Файл | Ответственность |
|---|---|
| `dispatcher/src/publish/index.js` | таблица площадок «готов ли / как отправить», правила и статусы |
| `dispatcher/src/publish/graph.js` | транспорт Meta Graph: POST/GET, перевод ошибок Meta в причины |
| `dispatcher/src/publish/threads.js` | Threads: контейнер → публикация (только текст) |
| `dispatcher/src/publish/instagram.js` | IG: карусель / обложка / Reels |
| `dispatcher/src/publish/media.js` | кадры из T10 → публичные HTTPS-ссылки для Meta |
| `dispatcher/src/publish/preflight.js` | предполётная проверка настройки: токены, права, статика |
| `dispatcher/src/publish/telegram.js` | TG-канал (T08), рядом для сравнения |
| `dispatcher/src/db/migrations/006_publish_refs.sql` | `published_ref` — id поста на площадке строкой |
| `dispatcher/scripts/smoke-ig-threads.mjs` | оффлайн-проверка всего перечисленного |
| `dispatcher/scripts/check-meta.mjs` | `npm run check:meta` — та же проверка из консоли VPS |
| `dispatcher/scripts/smoke-preflight.mjs` | оффлайн-проверка самой диагностики |

Добавить площадку = добавить запись в таблицу `PLATFORMS` (пара «ready» + «send»), а не править
`publishItem`.

## Threads (T11) — только текст

```
POST graph.threads.net/v21.0/{THREADS_USER_ID}/threads          media_type=TEXT&text=…  → creation_id
POST graph.threads.net/v21.0/{THREADS_USER_ID}/threads_publish  creation_id=…           → id поста
```

- Лимит поста — **500 знаков**. Длиннее — публикация отклоняется с причиной; текст **не режется
  молча**, потому что урезанный пост — уже не то, что одобрил владелец. Чинится «Правкой».
- Картинки Threads умеет, но здесь сознательно не используются: это отдельный формат и отдельное
  согласование.

## Instagram (T12) — карусель, обложка, Reels

```
карусель:  POST /{IG_USER_ID}/media  image_url=…&is_carousel_item=true   → id кадра (×N)
           POST /{IG_USER_ID}/media  media_type=CAROUSEL&children=id,id&caption=…
           POST /{IG_USER_ID}/media_publish  creation_id=…
обложка:   POST /{IG_USER_ID}/media  image_url=…&caption=…  → POST …/media_publish
Reels:     POST /{IG_USER_ID}/media  media_type=REELS&video_url=…  → ждать status_code=FINISHED
           → POST …/media_publish
```

- **Карусель — 2–10 кадров.** Один кадр публикуется обычным постом, одиннадцатый IG не примет
  (тот же потолок, что у media-group в Telegram, и тот же, что у рендера T10).
- **Подпись берётся из `meta.caption`** ответа агента, а НЕ из `item.content`: у карусели content —
  это спецификация слайдов Дизайнера, ей в подписи не место. Нет `caption` → пост уходит без
  подписи, и это проговаривается в топике, а не проглатывается.
- **Reels ждут видео.** `reels_script` без `meta.video_url` честно пропускается: сценарий — не
  ролик. Ролик монтируется на ноуте клиента (T15) и приезжает публичной ссылкой.
- **Reels публикуется не мгновенно.** Meta забирает ролик по `video_url` и обрабатывает его
  асинхронно; `media_publish` до `status_code=FINISHED` падает. Диспетчер опрашивает статус
  36 раз по 5 секунд (`IG_STATUS_ATTEMPTS`, `IG_POLL_MS`) — три минуты. Минуты, стоявшей здесь
  изначально, обычному ролику не хватает, а истёкшее ожидание — это не «подождём ещё», а
  `publish_failed` на исправном видео. Ожидание ничего не блокирует: кнопка «Одобрить»
  отвечается ДО публикации. Если три минуты всё же вышли, в ошибке сказано, сколько ждали, —
  чтобы ролик не начали перемонтировать на ровном месте.

## Гоча, определившая архитектуру: IG не принимает файл

Instagram Graph API берёт **только `image_url`/`video_url`** и скачивает медиа своими серверами.
Отрендеренный в T10 PNG лежит в `dispatcher/data/renders/` — наружу эта папка не смотрит, и
Meta до неё не достучится. Поэтому перед публикацией кадры **копируются в веб-корень**:

```
PUBLIC_DIR=/var/www/content-pipeline      # папка, которую раздаёт Nginx
PUBLIC_BASE_URL=https://media.example.com # её адрес снаружи (только https)
```

Ссылка собирается как `PUBLIC_BASE_URL/queue-<id>/slide-01.png`. Без этих двух переменных
IG-публикация невозможна **в принципе** — это устройство API, а не недоделка. Ошибка Meta на этот
случай (код 9004) переводится в понятное «ссылка должна быть публичной и по HTTPS».

## Что вводит клиент при установке

| Переменная | Откуда взять |
|---|---|
| `IG_USER_ID` | id бизнес-аккаунта Instagram (17841…) |
| `IG_ACCESS_TOKEN` | long-lived токен: `instagram_basic`, `instagram_content_publish`, `pages_read_engagement` |
| `THREADS_USER_ID` | id аккаунта Threads |
| `THREADS_ACCESS_TOKEN` | токен Threads-приложения: `threads_basic`, `threads_content_publish` |
| `PUBLIC_DIR`, `PUBLIC_BASE_URL` | папка Nginx-статики и её внешний адрес |
| `META_APP_ID`, `META_APP_SECRET` | **необязательно**, только для «/проверка»: developers.facebook.com → приложение → Settings → Basic. С ними видно, когда истекает токен |

**Токен от Instagram в Threads не работает и наоборот** — это разные приложения, разные хосты
(`graph.facebook.com` и `graph.threads.net`) и разные права. Самая частая ошибка настройки.

## Предполётная проверка (`npm run check:meta`, «/проверка»)

Креды клиента приезжают одним пакетом в день го-лайва, и проверять их реальными постами — плохая
идея: неудачная попытка либо оставляет мусор в аккаунте, либо возвращает одну строку ошибки Meta
без подсказки, что именно не так. Поэтому каждый шаг настройки проверяется отдельным безобидным
запросом, а ответ переводится в «что делать».

**Ничего не публикует.** Только GET-запросы плюс один временный файл в публичной статике, который
тут же удаляется. Поэтому проверка идёт по-настоящему даже при `PUBLISH_DRY_RUN=1`: сухой прогон
бережёт аккаунт от публикации, а здесь публиковать нечего.

| Что проверяется | Зачем именно это |
|---|---|
| файл записан в `PUBLIC_DIR` и **забран снаружи по https** | ровно это делает Instagram, когда качает медиа; не 200 → ни карусели, ни Reels |
| `GET /{IG_USER_ID}?fields=username,media_count` | токен рабочий, и видно, **в чей аккаунт** полетят посты |
| `GET /{IG_USER_ID}/content_publishing_limit` | требует того же права, что и публикация, но ничего не создаёт; плюс остаток суточной квоты |
| `GET /me` на `graph.threads.net` + сверка с `THREADS_USER_ID` | ловит подстановку инстаграмного id |
| совпадение токенов и id между площадками | самая частая ошибка: один токен вставлен в оба поля |
| `GET /debug_token` (нужны `META_APP_ID`/`META_APP_SECRET`) | срок жизни и права токена; необязательно, пропускается без них |

Почему лимит публикаций выбран как проверка права: это единственный эндпоинт, который требует
ровно `instagram_content_publish`, но не создаёт ни контейнера, ни поста.

Отчёт разделён по площадкам и заканчивается вердиктом «можно/нельзя публиковать» для каждой.
Статика блокирует Instagram, но не Threads: текстовому посту публичные ссылки не нужны.

Команда доступна двумя путями: `npm run check:meta` в консоли VPS (код возврата 1, если есть
блокирующие проблемы) и «/проверка» в топике Издателя — словами тоже: «проверь настройки».

## Сухой прогон (`PUBLISH_DRY_RUN=1`)

Проверить настройку, ничего не опубликовав: по «Одобрить» запросы в Meta **не уходят**, а в топик
Издателя печатается точный план вызовов. Статус элемента при этом **не меняется** — иначе БД
утверждала бы, что пост опубликован, хотя его нет. Убедился, что план верный → убрал переменную →
нажал «Одобрить» ещё раз.

На старте диспетчер печатает готовность каждой площадки:

```
  ✓ публикация tg
  — публикация threads: не задано в .env: THREADS_USER_ID, THREADS_ACCESS_TOKEN
  — публикация ig: не задано в .env: IG_USER_ID, IG_ACCESS_TOKEN
```

## Статусы

Те же, что в T08: `approved → published` (запоминается `published_ref`), `approved →
publish_failed` с причиной (повтор возможен после починки), `approved → scheduled → published`
для слота контент-календаря. Ненастроенная площадка даёт `publish_failed` с текстом «не задано в
.env: …» — молчания нет ни в одном сценарии.

**Почему `published_ref` — строка.** Id поста в IG и Threads — 17–18 цифр, это больше безопасного
диапазона целых в JavaScript (2^53): в числе такой id тихо теряет последние цифры, и пост по нему
потом не найти. Telegram-овский `published_message_id` остался как был.

## Проверка

```bash
cd dispatcher
node scripts/smoke-ig-threads.mjs   # оффлайн: fetch подменён, в Meta ничего не уходит
node scripts/smoke-preflight.mjs    # оффлайн: типовые ошибки настройки на поддельных ответах Meta
npm run smoke                       # он же в общей цепочке
```

Смоук проверяет шаги Graph API, публичные ссылки, лимиты (500 знаков / 10 кадров / 2200 подпись),
сухой прогон, сохранность 18-значного id и то, что неодобренное не публикуется.

**Живьём проверяется только на аккаунтах клиента** — нужны его Meta-приложения, бизнес-аккаунт IG
и Nginx-статика. Порядок на деплое:

1. заполнить креды в `.env` и поднять статику;
2. `npm run check:meta` (или «/проверка» у Издателя) → чинить по подсказкам, пока не зелено.
   Пока этот шаг красный, остальные бессмысленны: Meta вернёт ту же ошибку, но без объяснения;
3. поставить `PUBLISH_DRY_RUN=1`, одобрить тестовую карусель → план вызовов, ничего не уходит;
4. убрать `PUBLISH_DRY_RUN`, одобрить снова → пост в аккаунте;
5. то же для Threads с коротким текстом.

## Гочи

- **Контейнеры Meta живут ~24 часа.** Если публикация упала между шагами, повтор создаёт новые
  контейнеры — это нормально и ничего не ломает.
- **Обработка видео асинхронная.** Reels публикуется только после `status_code=FINISHED`; ждём
  36 × 5 с = 3 минуты (`IG_STATUS_ATTEMPTS`, `IG_POLL_MS`), дальше — честное «попробуй позже»
  с указанием, сколько ждали. Пауза между «Одобрить» и появлением Reels — норма, а не зависание.
- **Ошибки Meta приходят с `fbtrace_id`** — он сохраняется в объекте ошибки: с ним поддержка Meta
  ищет запрос, если дело дойдёт до неё.
- **Публичная папка накапливает картинки.** Кадры складываются в `PUBLIC_DIR/queue-<id>/` и не
  чистятся: пост в IG продолжает ссылаться на них уже после публикации. Чистка — вопрос эксплуатации
  (T17), а не публикации.
