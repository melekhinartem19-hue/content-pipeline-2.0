# Публикация живым браузером: Instagram и Threads (вариант C)

Альтернатива Graph API: диспетчер заходит в аккаунт клиента **как человек** и публикует через
веб-интерфейс. Включён решением владельца **15.09.2026** — причиной была не поломка API, а
трудоёмкость настройки Meta-приложения на стороне клиента.

> **Оба пути остаются рабочими.** Переключатель `IG_MODE` (`api` | `browser`) меняет только пару
> «готов ли / как отправить» в таблице `PLATFORMS`. Код Graph API не удалён и не тронут: если
> браузерная сессия упрётся в блокировку, возврат — это правка одной переменной и перезапуск.

## Чем за это платим (читать до включения)

Автоматизация веб-интерфейса **нарушает правила пользования Instagram**, и риск здесь несёт
**аккаунт клиента**, а не сервер. Худший исход — потеря рабочего аккаунта с аудиторией.
Это принятое решение владельца, а не недосмотр; здесь оно записано, чтобы через полгода никто
не считал это случайностью.

Что делается для снижения риска — и что **сознательно не делается**:

| Делаем | Не делаем |
|---|---|
| один вход, дальше постоянная сессия в профиле | не логинимся перед каждым постом |
| код проверки спрашиваем у владельца | не пытаемся обойти проверку |
| публикуем по факту одобрения, редко | не крутим ленту, не лайкаем, не подписываемся |
| честно падаем, когда сессия умерла | не «чиним» сессию автоматически втихую |

Средств обхода антибот-проверок в модуле нет и не планируется: подмены отпечатка браузера,
ротации прокси и имитации человеческого темпа здесь не будет.

## Что где живёт

| Файл | Ответственность |
|---|---|
| `dispatcher/src/publish/browser/selectors.js` | **все** селекторы IG и Threads — единственное место, где чинится редизайн |
| `dispatcher/src/publish/browser/session.js` | профиль браузера, вход, проверка/2FA, вход в Threads |
| `dispatcher/src/publish/browser/instagram.js` | мастер публикации: файлы → шаги → подпись → «Поделиться» |
| `dispatcher/src/publish/browser/threads.js` | текстовый пост: окно → текст → «Post» |
| `dispatcher/src/publish/browser/index.js` | точка входа для `PLATFORMS`, сухой прогон, отказы |
| `dispatcher/src/publish/browser/login-command.js` | «/вход» в топике Издателя и приём кода реплаем |
| `dispatcher/scripts/ig-login.mjs` | `npm run ig:login` — разовый вход из консоли VPS |
| `dispatcher/scripts/smoke-browser.mjs` | оффлайн-проверка (браузер не запускается) |

## Настройка

```bash
# dispatcher/.env — заполняется ТОЛЬКО на сервере
IG_MODE=browser
IG_LOGIN=<логин аккаунта клиента>
IG_PASSWORD=<пароль>
```

```bash
cd dispatcher && npm run ig:login     # разовый вход, код вводится в консоль
```

Дальше вход не нужен. Если сессия когда-нибудь умрёт — **«/вход»** в топике Издателя: код
придёт карточкой туда же, ответить надо реплаем. На сервер заходить не требуется.

Переменные `IG_PROFILE_DIR`, `IG_SHOTS_DIR` и `IG_HEADFUL` необязательны — см. `.env.example`.

## Команды в топике Издателя

| Команда | Что делает | Тратит `claude -p` |
|---|---|---|
| `/вход` | войти в оба аккаунта, код спросит карточкой | нет |
| `/вход статус` | живы ли сессии Instagram и Threads | нет |
| `/проверка` | предполётная проверка **API-пути** (при `IG_MODE=api`) | нет |

Команды распознаются и словами без слеша («перезайди», «сессия»), но **фраза целиком**: живая
речь вроде «не могу войти в инсту» уходит агенту, а не запускает браузер.

## Решения, которые нельзя менять не подумав

- **Признак «залогинены» — кука `sessionid`, а не элемент страницы.** Единственная проверка,
  которая переживает редизайн, смену языка и недокрутившуюся ленту.
- **Локаль контекста форсирована в `en-US`.** Селекторы держатся на видимом тексте кнопок, а
  Instagram переводит интерфейс по языку аккаунта. Клиент переключит язык — и без форса
  сломается всё сразу.
- **После успешного «Поделиться» ничто не имеет права бросить исключение.** Пост уже в ленте;
  падение на выемке ссылки пометило бы элемент `publish_failed`, владелец нажал бы «Одобрить»
  повторно — и в аккаунте оказалось бы **два одинаковых поста**.
- **Нет подтверждения публикации → просим проверить ленту глазами.** Пост мог уйти, а ответа мы
  не увидели. Молча повторять в такой ситуации опаснее, чем признать неопределённость.
- **Мастер проходится циклом «жми Next, пока не появится поле подписи».** Число промежуточных
  шагов Instagram меняет (обрезка, фильтры, выбор обложки) — фиксированная последовательность
  ломается на первом же изменении.
- **Подпись вводится `type()`, а не `fill()`.** Поле — `contenteditable`, и на программную
  подстановку значения обработчики Instagram не реагируют: подпись молча осталась бы пустой.
- **Браузер открывается и закрывается на каждую публикацию.** Постоянный профиль держит
  файловую блокировку: вечно открытый браузер не дал бы запустить `npm run ig:login` на том же
  сервере — ровно тогда, когда человек чинит вход.
- **Диспетчер не логинится сам во время публикации.** Сессия умерла — честный отказ. Автоматический
  повтор входа на каждой публикации это и есть тот признак, по которому аккаунты блокируют.
- **Ожидание кода живёт в ПАМЯТИ, а не в БД.** Оно привязано к живому браузеру и пережить
  перезапуск не может физически — в отличие от очереди согласования, которая обязана.
- **Ответ без цифр не снимает ожидание кода.** Промах реплаем или «сейчас посмотрю» не должны
  заставлять входить заново: каждый лишний вход повышает риск проверки.

## Что изменилось в требованиях к установке

- **Для каруселей и фото больше не нужны `PUBLIC_DIR` и `PUBLIC_BASE_URL`.** Браузер загружает
  файл, а не даёт Meta ссылку на скачивание. Публичная статика остаётся нужной PDF-воронке (T13)
  и приёму роликов (T15), но не постам.
- **Threads не нужен свой токен и своё приложение.** Он входит аккаунтом Instagram, профиль
  браузера один на обе площадки.
- **Reels пока всё же опирается на `PUBLIC_DIR`**: ролик с ноута кладётся в статику (T15), и
  браузер берёт оттуда файл с диска. Отвязать приём ролика от статики — отдельная задача.

## Проверено и не проверено

**Оффлайн (`npm run smoke`, `smoke-browser`):** переключатель `IG_MODE`, сухой прогон и его план,
отказы до запуска браузера (нет картинок, файла нет на диске, сценарий вместо ролика, пустой
текст), лимиты подписи и карусели, разбор адреса проверки, разбор команды «/вход», реестр
ожидающих кодов.

**Живьём не проверено ничего.** Селекторы формы входа и мастера публикации, загрузка файлов,
выемка ссылки на пост — всё это проверяется только на аккаунте клиента. Ожидаемо, что первый
живой прогон потребует правки одного-двух селекторов; для этого они и вынесены в отдельный файл
списками вариантов, а каждый сбой пишет скриншот в `IG_SHOTS_DIR`.

## Порядок первого живого запуска

1. `IG_LOGIN` / `IG_PASSWORD` в `dispatcher/.env` на VPS, `IG_MODE` пока оставить `api`.
2. `npm run ig:login` — пройти вход и проверку, код ввести в консоль.
3. `IG_MODE=browser` + `PUBLISH_DRY_RUN=1`, перезапуск → «Одобрить» печатает план, ничего не публикуя.
4. Снять `PUBLISH_DRY_RUN`, перезапуск → первая настоящая публикация, **смотреть глазами**.
5. `/вход статус` в топике Издателя — убедиться, что сессия жива после перезапуска.
