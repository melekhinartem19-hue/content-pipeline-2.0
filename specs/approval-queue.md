# Spec: Очередь согласования + карточки с кнопками (T07)

Ядро правила «публикация только после ок». Любой публикуемый черновик встаёт в очередь и
показывается карточкой с кнопками **Одобрить / Отклонить / Правка** в топике Издателя. Решение
живёт в БД, поэтому переживает перезапуск, а T08 берёт на публикацию только `approved`.

Определение агента-Издателя — [../agents/publisher.md](../agents/publisher.md) (он проверяет контент
перед публикацией, но сам не публикует и очередью не управляет — очередь это код, ниже).

## Одна лента согласования

Все карточки висят **в топике Издателя**, кто бы ни был автором черновика. Так владельцу не нужно
обходить топики агентов в поисках «что ждёт решения»; в топике автора черновик остаётся как есть.

## Что попадает в очередь

Решает не автор, а `kind` из META-конверта — см. [kinds.js](../dispatcher/src/queue/kinds.js):

| kind | площадка | |
|---|---|---|
| `tg_post` | `tg` | пост Сценариста |
| `carousel_spec`, `cover_spec` | `ig` | визуал Дизайнера (рендер — T10) |
| `reels_script` | `ig` | сценарий Reels (монтаж — T15) |
| `threads_post` | `threads` | текст под Threads (публикация — T11) |

Не согласовываются: `producer_plan` (раздача задач), `trend_report` (сырьё для тем),
`publish_check` (это сама проверка Издателя) и `pdf_spec` — лид-магнит инста-воронки идёт своей
веткой (T13), а не через ленту публикаций.

Привязка элемента к **одной** площадке — это и есть «3 раздельных согласования» из CLAUDE.md.

## Два входа в очередь

1. **Авто-раздача Продюсера (T05).** Исполнитель отработал → черновик уходит в топик автора и
   параллельно встаёт в очередь; в сводке раздачи видно `→ на согласование #N`.
2. **Прямое обращение к агенту** в его топике («Сценарист, напиши пост про X») → тот же путь.

Оба входа идут через одну функцию `enqueueAgentResult`, поэтому правила отбора едины.

## Жизненный цикл

```
draft → pending ──✅──> approved ──(T08)──> published
             ├──❌──> rejected
             └──✏️──> needs_edit ──реплай с правкой──> новая версия (pending)
                                                        старая → superseded
```

## Карточка и кнопки

`callback_data` = `q:<ok|no|ed>:<id>` (влезает в лимит 64 байта). **Идентификатор элемента зашит в
кнопку, состояние — в БД**, поэтому карточки остаются рабочими после перезапуска процесса. Связь
«сообщение ↔ элемент» хранится в `card_chat_id` / `card_message_id` — по ней бот находит, что
редактировать и к чему относится правка.

После нажатия карточка **редактируется на месте**: кнопки снимаются, в подвале появляется «кто и
что решил». Повторное нажатие по решённой карточке решение не перезаписывает — всплывает подсказка
«по #N решение уже принято».

Длинный черновик в карточке обрезается до 3000 символов с явной пометкой (лимит сообщения — 4096);
полный текст остаётся в топике автора.

## Выбор варианта поста

Сценарист присылает **2–3 варианта поста одним ответом**, разделённых строкой
`=== ВАРИАНТ N: угол ===`, и весь ответ становится ОДНИМ элементом очереди. Поэтому у карточки
появляется второй ряд кнопок — по кнопке на вариант (`callback_data` = `q:v<N>:<id>`):

```
[ Вариант 1 ] [ Вариант 2 ] [ Вариант 3 ]
[ ✅ Одобрить ] [ ❌ Отклонить ] [ ✏️ Правка ]
```

- Пока вариант не выбран, карточка показывает **все** тексты (выбирать вслепую по «углам» нельзя),
  а «Одобрить» отвечает всплывашкой «сначала выбери вариант». Без этой защиты в канал уехали бы
  все три варианта одним постом вместе со служебными разделителями.
- Нажатие «Вариант N» — **не решение**: статус остаётся `pending`, а в `content` элемента остаётся
  ровно выбранный текст. Публикация (T08/T11/T12) берёт `content` как есть и про варианты ничего
  не знает — вся логика заканчивается на карточке.
- Передумать можно до решения: исходный ответ агента целиком лежит в `meta.variants_source`,
  выбранный номер и угол — в `meta.variant_choice` / `meta.variant_angle`. Выбранная кнопка
  помечается галочкой, карточка перерисовывается на месте.
- «Отклонить» и «Правка» работают и без выбора — там вариант не нужен; на правку уходит весь
  исходный черновик.
- У черновика без разделителей (Threads-пост, спецификация Дизайнера) ряда вариантов нет вовсе —
  карточка выглядит как раньше.

## Цикл правки

«✏️ Правка» → статус `needs_edit` + подсказка «напиши правку ответом на эту карточку». Владелец
отвечает реплаем — **реплай однозначно связывает правку с элементом**, номер вводить не нужно.
Дальше диспетчер сам зовёт агента-автора через `claude -p` с промптом из трёх частей
([rework.js](../dispatcher/src/queue/rework.js)): исходная задача + предыдущая версия + правка —
агент между вызовами ничего не помнит, поэтому контекст кладётся в текст явно.

Новая версия встаёт в очередь новой карточкой (`parent_id`, `edit_note`), старая уходит в
`superseded` — **только после того, как новая реально встала**. Если доработка упала, элемент
остаётся `needs_edit`: правку можно прислать ещё раз.

## Команды в топике Издателя

| Команда | Что делает |
|---|---|
| `/очередь` | что ждёт решения + сводка по статусам (из БД, без `claude -p`) |
| `/слот 12 2026-09-05 10:00` | заготовка контент-календаря: отметка, когда публиковать элемент #12 |

Время слота хранится строкой как задал владелец и пока ни на что не влияет — расписание публикации
приедет в T08.

## Крайние случаи

| Ситуация | Поведение |
|---|---|
| Не задан `TOPIC_PUBLISHER` / `FORUM_GROUP_ID` | элемент всё равно в очереди, в ответ — честная ошибка; найдётся через `/очередь` |
| Повторное нажатие по решённой карточке | решение не меняется, всплывашка объясняет почему |
| Кнопка по удалённому/чужому элементу | понятная ошибка вместо падения бота |
| Чужая инлайн-кнопка (не `q:`) | игнорируется молча |
| «Одобрить» на черновике с вариантами без выбора | публикации нет, всплывашка «сначала выбери вариант» |
| Повторное нажатие того же варианта | ничего не переписывается (Telegram не любит правку сообщения без изменений) |
| Выбор варианта после решения | заблокирован: «по #N решение уже принято» |
| Агент упал на доработке | элемент остаётся `needs_edit`, попытку можно повторить |
| Перезапуск процесса | кнопки старых карточек работают: id в кнопке, состояние в БД |

## Проверка

```
cd dispatcher && npm run smoke      # smoke-queue + smoke-card + smoke-rework в общем прогоне
```

- `smoke-queue` — слой БД: карточка, версии, решения; отдельно **перезапуск** (запись в файловую БД,
  закрытие соединения, повторное открытие — карточка находится, решение на месте).
- `smoke-card` — реальный обработчик нажатий на фейковом ctx: смена статуса, снятие кнопок,
  идемпотентность, чужие и битые кнопки, обрезка длинного черновика.
- `smoke-variants` — разбор `=== ВАРИАНТ N ===`, кнопки вариантов, защита «Одобрить» без выбора,
  смена выбора, и главное — в канал уходит **один** вариант без служебных разделителей.
- `smoke-rework` — отбор публикуемого по `kind`, промпт доработки, круг правки (новая версия +
  `superseded`), падение доработки, авто-постановка в очередь из раздачи Продюсера, команда слота.

Живая проверка в группе (нужны токены): `npm run dev` → попросить Сценариста в его топике написать
пост → карточка появляется в топике Издателя → нажать «✏️ Правка», ответить реплаем «убрать эмодзи»
→ приходит новая версия → «✅ Одобрить» → `/очередь` показывает пусто, а элемент в БД — `approved`.
Нажатия кнопок делает человек: сымитировать их скриптом нельзя.
