# Spec: Публикация в TG-канал после «Одобрить» (T08)

Замыкает вертикальный срез Фазы 1: **тема → черновик → согласование → пост в канале**. Публикует
бот Издателя через Bot API — никакого Meta App Review здесь нет (правило 2 из CLAUDE.md касается
IG/Threads, это T11/T12).

## Главное правило

В канал уходит **только одобренный** элемент. Проверка живёт внутри `publishItem`
([publish/index.js](../dispatcher/src/publish/index.js)), а не у вызывающего, — обойти её мимо
кнопки нельзя. Черновик, отклонённый, отправленный на правку, заменённый и уже опубликованный
получают `skipped` с причиной.

## Когда публикуем

По кнопке **✅ Одобрить** — сразу. Исключение: если у элемента задан слот контент-календаря на
будущее (`/слот <id> 2026-09-05 10:00`), элемент уходит в `scheduled`, и его отправляет
планировщик ([publish/scheduler.js](../dispatcher/src/publish/scheduler.js)) — раз в минуту он
смотрит, чей слот уже наступил.

Слот распознаётся только в формате `YYYY-MM-DD HH:MM` (и ISO с `T`). Свободный текст («завтра в
10») сохраняется как пометка, но расписанием не считается: об этом сразу говорится в ответе на
команду, и публикация уйдёт сразу по «Одобрить». Так пользователь не думает, что запланировал,
когда не запланировал.

## Статусы

```
approved ──> published        (сразу по «Одобрить»)
approved ──> scheduled ──> published   (если задан слот на будущее)
approved ──> publish_failed ──> published  (после повторной попытки)
```

`published_message_id` и `published_at` сохраняются — по ним пост в канале можно найти позже
(метрика Аналитика — T16). `publish_error` хранит причину неудачи, элемент остаётся видимым.

## Текст и фото

| Случай | Как отправляется |
|---|---|
| только текст | `sendMessage`, длинный режется по 4096 |
| фото + текст ≤ 1024 | `sendPhoto` с подписью — один пост |
| фото + длинный текст | `sendPhoto` без подписи, затем текст сообщениями |

Картинку агент кладёт в META (`photo` / `photo_url` / `image`) — URL или локальный путь. Своих
картинок диспетчер не рисует: рендер каруселей и обложек это T10.

## Настройка

```
# dispatcher/.env
TG_CHANNEL_ID=@my_test_channel     # или -100…
```

**Бот Издателя обязан быть админом канала** с правом публикации, иначе Telegram отвечает
`Forbidden: bot is not a member of the channel chat` — эта ошибка попадёт в `publish_error` и в
топик Издателя, элемент останется неопубликованным.

Если `TG_CHANNEL_ID` не задан, диспетчер честно предупреждает об этом при старте, а «Одобрить»
отвечает ошибкой вместо тихого «ок».

## Крайние случаи

| Ситуация | Поведение |
|---|---|
| Бот не админ канала / канала нет | `publish_failed` + причина в БД и в топике; можно повторить |
| `TG_CHANNEL_ID` не задан | `failed` с прямым указанием, чего не хватает |
| Площадка `ig` / `threads` | `skipped` — «это T11/T12», ничего не отправляется |
| Слот в прошлом | публикуется сразу, а не «пропускается» |
| Перезапуск процесса с отложенным элементом | `scheduled` лежит в БД; уйдёт при следующем подъёме диспетчера |

## Проверка

```
cd dispatcher && npm run smoke      # smoke-publish в общем прогоне
```

`smoke-publish.mjs` (оффлайн, фейковый канал) проверяет: запрет публикации для всех статусов кроме
одобренного, текст/фото/подпись/нарезку, ошибку канала → `publish_failed` → повторную попытку,
отсутствие `TG_CHANNEL_ID`, отказ по чужой площадке, слоты (будущее/прошлое/свободный текст) и
работу планировщика.

Живая проверка (нужен тестовый канал и бот-админ в нём): `npm run dev` → попросить Сценариста
написать пост → карточка у Издателя → **✅ Одобрить** → пост появляется в канале, а в топике
Издателя — `📣 #N опубликован в канале`.
