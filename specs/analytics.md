# Аналитик: отчётность по конвейеру (T16)

Последний агент системы. Отвечает на вопрос владельца «а работает ли это вообще»: сколько сделано,
что не проходит согласование, где конвейер встал, что публикуется и как это заходит.

> Устройство системы и правила — [../CLAUDE.md](../CLAUDE.md). Контракт вызова агента —
> [agent-contract.md](agent-contract.md).

## Главное решение: цифры считает код, агент их объясняет

```
БД диспетчера ──▶ collectFacts()   ──▶ факты (числа)   ──▶ claude -p (Аналитик) ──▶ выводы
                  report.js            renderFacts()        ОДИН вызов на отчёт
```

Агенту нельзя поручать счёт: он ошибётся, а проверить будет нечем. Поэтому в промпте прямым
текстом: «цифры посчитаны диспетчером и верны — НЕ пересчитывай». Его работа — объяснить их и
предложить 2–4 действия.

Побочный эффект приятный: отчёт стоит **один** вызов `claude -p`, а не разбор базы вслух.

## Что попадает в отчёт

| Раздел | Откуда |
|---|---|
| Черновиков создано, решено, доля одобренного | `approval_queue` за период |
| Версий после правки, что ждёт решения сейчас | `parent_id`, статус `pending` |
| Что опубликовано: по площадкам и видам контента | `published_at`, `platform`, `kind` |
| Метрики постов (если включены) | `post_metrics`, последний снимок по каждому |
| Задачи Продюсера, сборы трендов, неиспользованные темы | `tasks`, `trend_runs`, `trend_topics` |
| Заявки на монтаж и PDF воронки | `video_jobs`, `funnel_pdfs` |

Период — `/отчёт` (7 дней), `/отчёт 30`, `/отчёт месяц`. Потолок — год: «за всё время» на растущей
базе превращается в простыню.

Граница периода считается в **UTC**, как `datetime('now')` в SQLite: строки дат в базе
сравниваются лексикографически, и локальное время здесь дало бы сдвиг.

## Метрики площадок — необязательная добавка

Отчёт полноценен **без них**: собственная база уже знает, что делается и где рвётся. Инсайты
Instagram и Threads требуют отдельных прав (`instagram_manage_insights`, `threads_manage_insights`),
а App Review мы не проходим (правило 2). На собственных аккаунтах в dev-mode клиент выдаёт их себе
сам — тогда включается `ANALYTICS_INSIGHTS=1`.

- Хранение — **по снимку на замер** (миграция `010_post_metrics`): охваты растут во времени, важна
  динамика, а не последняя цифра.
- Набор метрик — JSON: у Reels один, у карусели другой, у Threads третий, и Meta их меняет.
  Прибивать колонками — значит ловить миграцию на каждое изменение API.
- Отказ Meta (нет прав, пост слишком свежий) **не считается аварией**: отчёт выйдет без цифр
  площадки, а причина будет видна строкой. Аналитика не должна ронять конвейер.
- **Telegram в метриках нет**: Bot API не отдаёт просмотры постов канала, а заводить ради этого
  пользовательскую сессию мы не будем.

## Расписание

`/отчёт` руками — всегда. Автоотчёт включается `ANALYTICS_AT` (плюс `ANALYTICS_WEEKDAY`,
по умолчанию понедельник) и уходит в топик Аналитика раз в неделю.

Отметка «за какой день уже отчитались» лежит в БД (`app_state`, миграция `011`), а не в памяти
процесса: перезапуск диспетчера не должен присылать отчёт повторно. Отметка ставится **до** прогона —
отчёт идёт минуту-две, и следующий тик не должен запустить второй.

## Границы

- Отчёт **не идёт в очередь согласования**: `analytics_report` нет в `kinds.js` — это внутренняя
  аналитика для владельца, а не публикуемый контент.
- Без `agents/analyst.md` отчёт всё равно придёт — но только факты, с честной строкой «выводы не
  собраны».
- Аналитик **не открывает новых доступов**: он читает свою базу и, если включено, инсайты по уже
  опубликованному в аккаунты клиента.

## Проверка

Оффлайн: `npm run smoke` → `smoke-analytics` — период, разбивка по площадкам, подтягивание метрик,
разбор обоих форматов ответа Meta, отчёт без агента и расписание (в свой день, не дважды, переживает
перезапуск).
