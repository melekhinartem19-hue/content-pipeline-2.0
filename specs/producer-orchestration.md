# Spec: Продюсер — раздача задач и статус (T05)

Продюсер — оркестратор общей форум-группы. Владелец ставит цель в топике Продюсера → агент
раскладывает её на задачи → **диспетчер сам** разносит ТЗ по топикам исполнителей, запускает их
и показывает статус. Определение самого агента — [../agents/producer.md](../agents/producer.md).

## Главная гоча, из-за которой всё устроено именно так

**Telegram не доставляет ботам сообщения других ботов.** ТЗ, которое бот-Продюсер постит в топик
Сценариста, сам бот-Сценарист **не увидит** — его хендлер не сработает. Поэтому «бот пишет боту»
как механизм невозможен, и цепочку замыкает диспетчер: он один процесс, внутри которого живут все
6 бот-идентичностей, и он вызывает агента-исполнителя напрямую через контракт `runAgent`
(`claude -p`), а результат постит в топик исполнителя **от имени его бота**. Снаружи это выглядит
как живой конвейер, где агенты общаются друг с другом.

## Поток одной задачи

```
владелец пишет цель в топике Продюсера
   → runAgent('producer')  → план + META { kind:"producer_plan", title, tasks:[{agent, brief}] }
   → план показан в топике Продюсера
   → extractTasks()        → отсев мусора (неизвестный агент / пустое ТЗ / лимит)
   → на каждую задачу:
        tasks(queued) в БД
        ТЗ → топик исполнителя      (постит бот-Продюсер)
        tasks(running) → runAgent(исполнитель) → claude -p
        черновик → тот же топик      (постит бот-исполнитель)
        публикуемый черновик → очередь согласования карточкой (T07)
        tasks(done | failed)
   → сводка раздачи в топик Продюсера
```

Черновик исполнителя не остаётся «просто сообщением»: если его `kind` публикуемый, он тем же
проходом встаёт в очередь согласования и в сводке видно `→ на согласование #N`. Правила отбора —
[approval-queue.md](approval-queue.md).

## Состояние задачи

`queued → running → done | failed`. Хранится в `tasks`: `agent`, `brief`, `goal`, `topic_id`,
`status`, `result` (выжимка ≤300 символов), `error`. Полный текст черновика в БД не дублируется —
он уходит в топик; в очередь согласования черновики лягут в T07.

## Ответу агента не доверяем

`meta.tasks` — текст от языковой модели, поэтому `extractTasks` проверяет каждую задачу:

- агент должен быть среди **поднятых** ботов-исполнителей (Продюсер и спайн-бот T01 исключены —
  себе задач не ставим);
- `brief` непустой; регистр и пробелы нормализуются;
- не больше `MAX_TASKS_PER_PLAN = 6` задач на план (каждая = тяжёлый `claude -p`).

Отсеянное не теряется: причина попадает в сводку раздачи («⚠️ пропущено → video — нет такого
агента»).

## Порядок и нагрузка

Исполнение **последовательное** — внутри `orchestrator.js` живёт общая очередь-цепочка промисов,
чтобы два плана не запустили несколько `claude -p` разом. Падение одной задачи очередь не рвёт.

## Команда статуса

`/статус` (`/status`, «статус») в топике Продюсера отвечает **из БД, минуя `claude -p`**: у агента
один проход без доступа к очереди, статусы помнит диспетчер. Вывод: сводка по состояниям + до 15
последних задач с ТЗ в одну строку; у `failed` — текст ошибки.

Распознавание — `(?![\p{L}\p{N}_])` с флагом `u`, а не `\b`: `\b` не считает кириллицу за букву,
и «статус» в конце строки не совпал бы вовсе.

## Крайние случаи

| Ситуация | Поведение |
|---|---|
| Продюсеру написали в личку (нет `FORUM_GROUP_ID`) | план показан, раздача пропущена с честным «работает только в форум-группе» |
| У исполнителя не задан `TOPIC_*` в `.env` | задача пишется в БД как `failed` с подсказкой про переменную, в Telegram ничего не шлётся |
| Агент упал / тайм-аут `claude -p` | `failed` + текст ошибки в БД и в топик исполнителя |
| Просто вопрос Продюсеру (`tasks: []`) | ответ показан, раздачи нет |
| Ошибка самой оркестрации | логируется, ответ пользователю не рушится |

## Проверка

```
cd dispatcher && npm run smoke      # smoke-tasks + smoke-orchestrator в общем прогоне
```

`smoke-orchestrator.mjs` гоняет весь путь оффлайн: вместо `claude -p` и Telegram — инъекции
`runner`/`poster`, проверяются успех, падение агента, отсутствие топика, сводка и статус.

Живая проверка — `npm run live:t05 "нужен 1 пост про запуск тарифа"`
([scripts/live-orchestration.mjs](../dispatcher/scripts/live-orchestration.mjs)): реальные токены,
реальные топики, реальный `claude -p`. ⚠ Скрипт **пишет в группу** и тратит вызовы Claude.

**Проведена 04.09.2026, зелёная:** Продюсер разложил цель на 1 задачу Сценаристу → ТЗ ушло в топик
2 от бота-Продюсера → Сценарист отработал за ~27 с и положил туда же готовый пост от своего бота →
в БД `#1 writer done`, сводка и статус легли в топик Продюсера (14).

Входящий хоп (человек пишет в топик → роутер → агент) этим скриптом не покрыт и покрыт быть не
может: бот не получает сообщений другого бота. Он проверяется вживую в T03 и повторяется вручную —
`npm run dev`, написать цель в топике Продюсера, затем `/статус` там же.
