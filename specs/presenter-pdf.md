# Spec: PDF-лид-магниты инста-воронки (T13)

Структура Презентатора превращается в **готовый PDF формата A4**, файл выкладывается в публичную
статику Nginx, а его адрес сохраняется в БД — по этим трём ссылкам воронка ManyChat (T14) отвечает
в директе. Тем ровно три, они заданы конфигом, а не решением агента.

Модуль сборки — тот же самый `render/`, что рисует карусели (T10): у него уже есть браузер, тема
из «мозга бренда» и разбор ответа агента. Мост в Telegram и БД — `dispatcher/src/funnel/`.

## Поток

```
manychat/funnel.json  (три темы: key, title, brief, keyword)
        │
        ▼  на каждую тему — один вызов
   claude -p → agents/presenter.md → «=== СТРАНИЦА N ===» + META (kind: pdf_spec)
        │
        ▼  render/pdf.js
   HTML-документ (все листы разом) → headless Chromium → page.pdf() → dispatcher/data/pdf/<key>.pdf
        │
        ├──▶ копия в PUBLIC_DIR/funnel/<key>.pdf → https-ссылка (PUBLIC_BASE_URL)
        ├──▶ строка в таблице funnel_pdfs (key, title, file, url, pages) — её читает T14
        └──▶ файл документом в топик Презентатора + отчёт со ссылками
```

## Почему PDF идёт мимо очереди согласования

Через очередь (T07) проходит то, что публикуется **в ленту**, и решение владельца там — «постить
или нет». Лид-магнит в ленту не уходит: он лежит в статике и выдаётся по запросу в директе.
Поэтому `pdf_spec` в очередь не пускается (`queue/kinds.js`), а владелец смотрит **готовый файл**
прямо в топике Презентатора и при желании пересобирает тему одной командой.

## Формат листа: A4, а не 4:5

Решение владельца (07.09.2026). Лид-магнит читают вне ленты — с телефона, с ноутбука, иногда
печатают; A4 — то, чего человек ждёт от файла «скачать гайд». Вертикаль 1080×1350 в PDF читалась бы
как «карусель, зачем-то склеенная в документ».

Технически лист — **794×1123 CSS-пикселя** (это A4 с точностью до десятой миллиметра). Одно и то же
число стоит в трёх местах: `@page { size }`, правило `.page` и параметры `page.pdf()`. Расхождение
даже в полмиллиметра ломает документ (см. «Гочи»).

## Роли страниц

Роль решает вёрстку и назначается по позиции — так же предсказуемо, как у слайдов:

| Роль | Кто | Как выглядит |
|---|---|---|
| `cover` | первая страница | обещание результата крупно, подводка под ним, акцентная плашка |
| `body` | середина | заголовок-подводка с акцентной чертой, текст по центру листа |
| `cta` | последняя (если страниц ≥ 3) | лист залит акцентом, текст контрастным цветом |

Больше **12 страниц** не собираем: обложка + 3–8 раскрытия + финал — это ~10, дальше начинается уже
брошюра. Хвост отбрасывается, и об этом говорится в подписи под файлом.

## Конфиг трёх тем

Видимый файл `manychat/funnel.json` (шаблон — `funnel.example.json`, описание — `manychat/README.md`).
Поля: `key` (латиницей — он же имя файла и часть ссылки), `title`, `brief` (это и есть задача
агенту), `keyword` (триггер в директе, нужен T14), `pages` (ориентир по объёму).

Проверка конфига идёт **до** вызовов агента: кривой ключ, дубль ключей и пустой `brief` ловятся
раньше, чем потрачены три вызова `claude -p`. Тем не три — не ошибка, но об этом говорится вслух:
воронка рассчитана ровно на три кнопки (правило CLAUDE.md — матчинг без ИИ-классификации).

## Команда `/пдф`

В топике Презентатора:

| Команда | Что делает |
|---|---|
| `/пдф` | собрать все темы: по вызову агента и рендеру на тему |
| `/пдф <ключ>` | пересобрать одну тему (например, `/пдф content-plan`) |
| `/пдф список` | показать, что воронка отдаёт сейчас — чтение из БД, без агента и браузера |

Расписания у сборки нет и не планируется: темы меняются раз в сезон, а каждый прогон — это три
вызова Claude и три запуска браузера.

## Хранение и ссылки

Таблица `funnel_pdfs` (миграция 007) — **строка на тему**, ключ темы и есть первичный ключ.
Пересборка перезаписывает строку, поэтому уже разосланная ссылка остаётся живой: меняется файл по
тому же адресу, а не адрес.

Ссылка складывается из `PUBLIC_BASE_URL` + `funnel/<key>.pdf` (подпапка — `PDF_PUBLIC_SUBDIR`).
Без `PUBLIC_DIR`/`PUBLIC_BASE_URL` файлы всё равно собираются и лежат локально, но `url` остаётся
пустым, а в отчёте появляется подсказка, что настроить: **выдумывать адрес нельзя** — по нему
человек в директе получит 404.

## Правило «одна тема не роняет остальные»

Каждая тема — отдельный вызов `claude -p` (деньги и время) плюс отдельный рендер. Сбой на одной
теме не отменяет две другие: причина запоминается в результате, печатается в отчёте, цикл идёт
дальше. То же и со статикой: не скопировалось в публичную папку — файл всё равно собран и записан.

## Гочи

- **«A4» словом ≠ 210 мм.** Chromium считает бумагу A4 как 594.96×841.92 pt (209.89×297.0 мм), и
  лист шириной ровно 210 мм в неё не влезает: каждая страница роняет полоску на следующую, и в
  файле выходит вдвое больше листов, половина пустых. Проверено: 5 страниц превращались в 11.
  Поэтому размер задан числом (794×1123 px) и одинаков в CSS и в вызове `page.pdf()`.
- **Разрыв страницы — ПЕРЕД листом, а не после.** Лист ровно в высоту бумаги уже заполняет её
  целиком, и `break-after: page` добавляет к каждому листу пустой.
- **`printBackground: true` обязателен.** Без него Chromium печатает без фонов: фирменный фон и
  акцентная заливка финальной страницы исчезают, документ выходит белым.
- **Плейсхолдер в комментарии шаблона тоже подставляется.** `{{PAGES}}`, написанный в
  документирующем комментарии, вставил туда копию всех страниц — а комментарий страничного
  шаблона своим `-->` закрыл чужой комментарий, и документ собрался дважды.
- **Файл-PDF в Instagram-директ отправить нельзя** — только ссылку (правило CLAUDE.md). Поэтому
  публичная статика для воронки не «желательна», а обязательна.
- **На VPS нужны браузер и кириллические шрифты** — те же, что для картинок:
  `sudo apt-get install -y chromium fonts-dejavu fonts-noto-core`. Иначе страницы выйдут
  квадратиками.

## Проверка

```bash
cd render && npm run demo:pdf      # пример структуры → render/out/demo.pdf, посмотреть глазами
cd dispatcher && npm run smoke     # smoke-pdf (структура, вёрстка, настоящий PDF) + smoke-funnel
npm run live:t13                   # ⚠ ЖИВОЙ прогон: три вызова claude и файлы в топик
npm run live:t13 content-plan      # то же для одной темы
```

`smoke-pdf` проверяет в том числе, что **листов в файле ровно столько, сколько страниц в
структуре** — именно эта проверка ловит «лишние пустые листы» при любом расхождении размеров.
`smoke-funnel` проверяет диспетчерскую часть на фейках: сколько вызовов агента ушло, куда
скопированы файлы, что попало в БД и что происходит, когда одна тема упала или статики нет.
